# RS485 采集报文节流与配置运行时刷新 Spec

## 状态

Approved for implementation

关联决策：[ADR-0013](../adr/0013-rs485-request-pacing-and-runtime-reconfiguration.md)、[ADR-0014](../adr/0014-raw-register-acquisition-before-protocol-parsing.md)

## 目标

在第一阶段馈电保护器 RS485 Modbus RTU 采集闭环中，增加通道级报文间隔延迟，并使通信通道和采集设备的管理配置在数据库提交成功后能够刷新到运行中的采集器。

本 Spec 只调整采集调度、通道节流和配置生效方式，不扩大第一阶段范围：仍不接入 MQTT、告警、控制、Modbus Server、TCP / UDP 或历史数据存储。

## 术语与语义

### 采集周期

`pollIntervalMs` 是设备级配置，表示一次设备完整采集结束后，等待多久再安排该设备下一次采集。它控制设备数据刷新频率，不控制连续 Modbus 请求之间的间隔。

### 报文间隔延迟

`interRequestDelayMs` 是通道级配置，表示同一通道上一条 Modbus 请求完成后，下一条请求发送前增加的业务等待时间。

它同时作用于：

- 同一设备的连续寄存器读取块之间；
- 同一通道不同设备的读取之间；
- 后续接入该通道的其他 Modbus 请求。

值为 `0` 时不增加业务等待，但底层 Modbus RTU 客户端仍负责协议要求的 `t3.5` 帧间静默。

## 功能要求

### FR-1 通道配置

通信通道增加字段：

| 领域字段 | JSON 字段 | 数据库字段 | 类型 | 范围 | 默认值 |
|---|---|---|---|---:|---:|
| 报文间隔延迟 | `interRequestDelayMs` | `inter_request_delay_ms` | `int` | 0～60000 | 0 |

要求：

- PostgreSQL 和 SQLite schema 同步增加字段；
- 已有通道迁移后值为 `0`；
- API 创建和更新允许缺省或显式传入 `0`；
- 小于 `0` 或大于 `60000` 返回参数错误；
- 查询、创建和更新响应均返回该字段；
- React 通信通道表单允许输入 `0～60000`，并说明 `0` 只使用 RTU 协议自身间隔。

### FR-2 请求节流

同一通道所有 Modbus 请求必须经过一个串行的通道级 paced session：

```text
请求 A 发送 → 等待 A 的响应/失败结束
             → 等待 interRequestDelayMs
             → 请求 B 发送
```

要求：

- 通道打开后的第一条请求不增加业务延迟；
- 底层 RTU `t3.5` 与业务延迟叠加，不由业务层替代；
- 失败或超时的请求也视为一次已结束事务，后续请求仍遵守业务延迟；
- 同一设备的连续读取块之间必须受该延迟约束；
- 不得通过协议适配器中的散落 `sleep` 绕过通道节流；
- 不同通道之间可以并行，不得互相等待。

### FR-3 设备采集调度

每个启用设备继续使用自身的 `pollIntervalMs`：

- 设备一次完整采集成功或失败后，下一次到期时间按完成时间加采集周期计算；
- 同一通道永不并发发送请求；
- 设备读取耗时超过周期时不补发、不追赶、不形成连续重试；
- 多个设备同时到期时按 `nextDue` 升序处理，时间相同按设备 ID 升序处理；
- 报文节流导致实际周期变长时允许自然延迟，不自动修改设备配置；
- 新增或重新启用设备在下一次调度时立即进行首次采集；
- 单个读取块失败后继续处理该设备的后续读取块；
- 单设备失败不得永久阻塞同通道其他设备。

### FR-4 运行时配置刷新

采集配置写操作成功提交数据库后，必须通知运行时刷新启用配置。以下操作均属于刷新范围：

- 通道新增、修改、删除、启用、禁用；
- 设备新增、修改、删除、启用、禁用；
- 设备所属通道或 Modbus 地址修改；
- 寄存器读取块新增、修改、删除或排序变化；
- 通道物理串口参数修改；
- 报文间隔延迟和设备采集周期修改。

刷新边界：

- 当前设备完整采集结束后才可应用新快照；
- 调度参数变化无需重建串口，下一次请求使用新值；
- 端口、波特率、数据位、停止位、校验和通信超时变化需要在通道边界重建会话；
- 新会话打开失败时停止旧会话，运行时记录错误并按新配置重试；
- 运行时应用失败不回滚已提交的数据库配置；
- 被禁用或删除的设备从当前状态集合移除；
- 没有启用设备的通道不保持打开的串口会话。

### FR-5 当前状态

继续使用进程内当前状态，不把每轮数据写入数据库。运行时刷新后：

- 保留仍启用设备的已有当前数据和通信状态；
- 删除或禁用的设备从当前状态列表移除；
- 新增或重新启用的设备先进入初始状态，首次采集立即尝试；
- 读取块名称或排序变化保留已有快照，功能码、起始地址或数量变化清除旧快照；
- 配置刷新失败通过采集日志记录，不新增调度器内部字段到 `/states` 契约。

## API 与页面契约

通道 API 的 JSON 字段增加：

```json
{
  "interRequestDelayMs": 0
}
```

React 页面要求：

- 通道表单新增“报文间隔延迟（毫秒）”；
- 默认值为 `0`；
- 最小值为 `0`，最大值为 `60000`；
- 通道列表显示该值；
- 不再提示“修改后必须重启服务生效”；
- 设备表单继续展示“采集周期（毫秒）”，保留其设备级语义。

## 数据库迁移

新增 acquisition channel migration，PostgreSQL 和 SQLite 版本号锁步：

- `inter_request_delay_ms INTEGER NOT NULL DEFAULT 0`；
- 保持已有通道数据可读；
- 不改变设备唯一约束、启用状态或删除语义。

## 实现边界

推荐的实现边界：


1. `Channel`、输入 DTO、Repository 和 React 类型增加新字段。
2. 在通道级 Modbus session 之上实现请求节流，维护“上一次请求事务完成时间”。
3. 运行时把每个通道的设备集合和调度状态作为可替换快照，保证单通道内切换不与当前请求并发。
4. 配置写入成功提交后，通过运行时刷新入口提交新启用配置。
5. 物理串口参数变化先结束旧会话，再按新配置打开；打开失败则保持无会话并重试新配置，不能继续使用旧配置。
6. 读取块按顺序独立执行，单块失败不阻止后续块，并按 ADR-0014 更新部分成功状态。

## 验收标准

### 后端单元测试

- `interRequestDelayMs=0` 时不增加业务 sleep；
- `interRequestDelayMs>0` 时，同一设备连续读取块和不同设备读取之间均满足最小额外延迟；
- 第一条请求立即发送；
- 请求失败后下一次请求仍遵守延迟；
- 单设备读取超时不触发追赶；
- 多个设备同时到期按 `nextDue`、设备 ID 顺序执行；
- 新增/启用设备首次调度立即尝试；
- 禁用/删除设备从当前状态移除；
- 调度参数变化不重建串口，物理参数变化在通道边界重建；
- 新会话打开失败时旧配置不继续发送，运行时进入重试路径。

### PostgreSQL / SQLite 集成测试

- migration 能创建默认值为 `0` 的新字段；
- 通道创建、查询、修改均能持久化和返回新字段；
- `-1` 和 `60001` 被拒绝；
- 缺省字段兼容已有 API 调用；
- 设备和通道配置写成功后能够触发运行时刷新入口。
- 读取块写成功后能够触发运行时刷新入口。

### 前端验证

- 通道表单能编辑和提交 `0～60000`；
- 表格和详情显示报文间隔延迟；
- 设备采集周期仍按设备维度展示；
- 执行 `task frontend:lint` 和 `task frontend:build` 通过。

### 联调验证

使用至少两个同通道 Modbus Slave：

- 可观察到同一通道请求严格串行；
- 两个连续读取块及不同设备请求之间存在配置的额外间隔；
- 一台设备超时不会使另一台设备停止；
- 修改通道延迟或设备周期后无需重启即可影响后续请求；
- 修改串口参数后会话按新配置重建；
- 禁用设备后不再发送其请求。

## 非目标

- 不把不同功能码或不连续地址的读取块合并为一次请求；
- 不引入 MQTT、告警、控制、Modbus Server、TCP / UDP；
- 不建设实时数据历史库；
- 不引入复杂优先级调度或通用任务编排器；
- 不支持直接修改数据库后自动发现配置变化；
- 不把调度器内部的实际等待时间加入当前状态 API。
