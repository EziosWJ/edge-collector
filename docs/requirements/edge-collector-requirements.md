# Edge Collector 需求基线

> 状态：Draft / 需求评审阶段
>
> 本文描述 Edge Collector 当前已确认的业务目标、运行约束和能力边界。本文不规定内部接口、类、函数、任务队列、线程/协程模型或具体协议抽象方式；这些内容在需求确认后进入技术设计阶段决定。

## 1. 项目目标

Edge Collector 是运行于工业现场边缘设备上的数据采集与协议接入服务，目标平台包括 RK3568 + Buildroot / Ubuntu。

系统负责连接现场设备，持续采集设备数据、监测告警、接收远程控制指令，并向上级系统提供 MQTT 数据交互和 Modbus Server 数据服务。

当前后端采用 Go；SQLite + CGO 的 ARM64 静态交叉编译已经在 RK3568 实机验证通过。数据库和现有管理后台属于项目基础设施，不代表采集领域的内部实现已经确定。

## 2. 现场设备与通信方式

系统需要支持以下设备通信方式：

- RS485 串口；
- TCP；
- UDP。

现场设备主要采用 Modbus 协议。根据具体设备，可能存在：

- Modbus RTU；
- Modbus TCP；
- 基于 TCP 传输的 Modbus RTU 报文；
- Modbus RTU over UDP；
- 厂家定义的、以 Modbus 报文为基础的其他传输方式。

系统必须允许不同设备型号在寄存器地址、功能码、数据格式、字节序、换算规则、告警流程和控制流程上存在差异。

## 3. RS485 现场约束

典型硬件最多约 8 路 RS485 串口。

当前业务约束：

- 同一路串口原则上挂载相同类型设备；
- 单路串口原则上最多约 8 台设备；
- 同一路总线设备通过 Modbus 地址区分；
- 同一物理串口上的通信必须避免报文冲突；
- 不同串口应能够独立工作；
- 单个设备故障不得长期阻塞同通道或其他通道的后续工作。

具体串口数量、设备数量、波特率和通信参数由项目配置决定。

## 4. 实时数据采集

设备运行期间，实时数据需要持续轮询采集。

基本业务行为：

```text
持续轮询设备
  ↓
获取实时数据
  ↓
解析有效数据
  ↓
按上报要求发送到 MQTT
  ↓
进入下一轮采集
```

实时数据可能包括遥测、遥信、电压、电流、功率、开关状态、运行状态、设备运行参数及其他业务数据。

要求：

- 实时采集不能执行一次后停止；
- 不同设备或数据类别允许配置不同采集周期；
- 单次超时或异常后应继续后续采集；
- 单个异常设备不得导致其他设备长期停止采集；
- 具体一次读取多少寄存器、如何拆分请求不在需求阶段规定。

## 5. 告警监测

部分设备不会主动推送告警，因此系统需要持续轮询告警状态。

告警业务行为：

```text
持续检测告警状态
  ↓
未触发 ──→ 继续检测
  ↓ 触发
按该设备协议获取告警详情
  ↓
解析告警
  ↓
立即上报 MQTT
  ↓
继续告警检测
```

要求：

- 未触发告警时继续轮询，不结束告警检测；
- 触发告警后，应及时执行该设备要求的后续查询流程；
- 告警详情获取成功后应即时上报，不等待普通实时数据的上报周期；
- 告警处理完成后继续后续告警检测；
- 不同设备允许有完全不同的告警触发条件、查询步骤、确认方式和数据格式。

### 5.1 已知设备协议示例

某设备存在如下告警流程：

1. 持续读取寄存器 812；
2. 值为 0 时表示当前没有新的告警；
3. 值非 0 时表示存在新的告警；
4. 向寄存器 8166 写入 0；
5. 查询最近一条告警；
6. 告警内容位于寄存器 8167～8180；
7. 解析后立即 MQTT 上报；
8. 随后继续告警轮询。

该流程仅是具体设备协议示例，不定义所有设备的统一内部接口。

## 6. MQTT 上行与下行

系统需要作为 MQTT Client 连接上级 Broker。

MQTT 至少承担：

- 实时数据上报；
- 告警数据上报；
- 设备通信状态上报；
- 控制结果上报；
- 接收上级控制指令。

当前需求阶段不固定 Topic 命名、Payload 格式、QoS、retain 等具体接口协议；这些内容需要结合上级平台接口进一步确认，并应支持按项目配置或接口规范确定。

## 7. 远程设备控制

部分现场设备需要接收上级平台下发的操作，例如分闸、合闸及其他设备特定操作。

基本业务行为：

```text
收到 MQTT 控制指令
  ↓
识别目标设备与操作
  ↓
按照该设备协议执行控制
  ↓
获得执行结果
  ↓
反馈结果
```

要求：

- 不同设备允许拥有不同控制地址、报文、执行步骤和结果确认方式；
- 控制指令具有较高时效性，应在合理时间内得到处理；
- 控制执行不能造成普通实时采集永久饥饿；
- 设备离线、通信超时、协议异常等情况下需要明确反馈失败结果；
- 是否需要控制前置条件、二次确认、超时后的结果查询等，按具体设备协议确定。

## 8. 通信协调

实时采集、告警检测、告警详情查询和远程控制可能同时竞争同一现场通信通道。

系统需要保证：

- 同一路 RS485 总线上的事务有序，不发生并发报文冲突；
- 不同独立通信通道可以互不阻塞地工作；
- 告警和控制等高时效业务能够及时处理；
- 普通实时采集不能长期得不到执行；
- 通信超时后能够释放当前工作并继续后续工作；
- 不因单个设备异常导致整体采集服务停止。

需求阶段不规定使用队列、goroutine、线程、事件循环或其他具体调度实现。

## 9. 设备在线与异常状态

系统需要维护设备通信状态，并能识别至少以下状态变化：

- 正常通信；
- 暂时通信失败；
- 长时间无响应 / 离线；
- 通信恢复。

具体离线判断阈值、连续失败次数、恢复判定规则和超时时间应允许根据项目配置。

状态变化需要能够向上级系统报告。

## 10. Modbus Server 对外数据服务

Edge Collector 还需要作为 Modbus Server，为其他设备或系统提供指定数据。

要求：

- 对外提供的数据来源于 Edge Collector 已采集或维护的数据；
- 可以对外提供实时数据、设备状态、开关状态及其他指定业务数据；
- 对外寄存器地址由项目接口要求定义；
- 对外寄存器地址不要求与现场设备原始寄存器地址一致；
- 当现场设备失去通信时，应能区分“最后一次有效值”和“当前通信状态”，避免历史值被误认为当前实时值。

具体数据映射机制、内部缓存结构和 Modbus Server 实现方式在技术设计阶段决定。

## 11. 配置需求

以下信息原则上需要可配置：

- 通信通道：串口、波特率、校验方式、TCP/UDP 地址和端口、超时等；
- 设备：唯一标识、名称、型号、类型、Modbus 地址、所属通道、启停状态；
- 采集：实时采集周期、告警检测周期、超时和重试相关参数；
- MQTT：Broker、认证信息、连接和消息相关参数；
- Modbus Server：对外服务参数和数据映射要求；
- 设备状态判定相关阈值。

配置文件格式、数据库表结构和热加载方式不在本需求阶段固定。

## 12. 本地持久化边界

项目已经正式支持 SQLite 单实例本地文件部署，同时保留 PostgreSQL 支持。

对于 Edge Collector：

- SQLite 适合保存设备配置、通信配置、系统配置、用户权限、必要业务记录等需要持久化的数据；
- 高频实时采集值不应因为“已有 SQLite”就默认逐点、逐周期全部持久化；
- 是否保存实时历史数据、保存多久、保存粒度如何，需要作为独立业务需求确认；
- MQTT 上报、Modbus Server 对外读取和当前设备状态不应强制依赖每轮数据写数据库后才能继续。

## 13. 稳定性与可运维性

系统需要长期连续运行，并满足：

- 单个设备异常不导致整个服务退出；
- 单一路通信异常不影响其他独立链路；
- TCP / MQTT 等连接中断后具备恢复能力；
- 串口或设备短时异常恢复后能够继续采集；
- 避免异常任务无限堆积；
- 避免长期运行过程中资源无界增长；
- 关键启动、停止、通信异常、设备上下线、告警和控制结果需要有可排障记录；
- 高频正常采集不应产生无法控制的日志量；
- 进程异常退出后允许由操作系统服务管理机制重新拉起。

## 14. 目标规模

典型目标规模：

```text
最多约 8 路 RS485
×
每路原则上最多约 8 台设备
```

此外可能同时存在 TCP / UDP 设备、MQTT 连接以及 Modbus Server 对外访问。

具体性能验收数字需要在设备协议、轮询周期、波特率和目标硬件配置明确后确定。目前不人为承诺固定 TPS 或毫秒级延迟指标。

## 15. 已确定的技术基线

以下已经确定或完成验证，不再作为本轮语言选型问题：

- 开发语言：Go；
- 仓库：`EziosWJ/edge-collector`；
- 目标平台：RK3568 ARM64，Buildroot / Ubuntu；
- 当前工程形态：单仓库、Go 后端 + React 管理后台；
- SQLite：正式支持单实例本地文件部署；
- SQLite + CGO：Zig + musl ARM64 静态交叉编译已实机验证；
- 当前继续沿用模块化单体，不提前拆微服务。

相关已有决策见 `docs/adr/`，ARM64 实机记录见 `docs/sqlite-arm64-test-deployment.md`。

## 16. 本阶段明确不固定的内容

在需求评审完成前，不提前写死：

- `ReadRealtime()`、`CheckAlarm()`、`ReadAlarm()` 等设备接口；
- `Open()`、`Close()`、`Reset()` 等控制接口；
- `ReadHoldingRegisters()`、`WriteSingleRegister()` 等底层 Modbus API 封装形态；
- Device Driver / Plugin 的具体抽象；
- 内部任务类型和任务队列；
- goroutine / worker / event loop 等并发模型；
- 数据缓存的具体结构；
- MQTT Topic / Payload 最终协议；
- Modbus Server 的内部寄存器映射实现；
- 配置热加载机制；
- 高频实时数据历史存储方案。

## 17. 需求评审出口

需求阶段完成的最低条件：

1. 明确首期要接入的设备与通信方式；
2. 明确实时数据采集和上报语义；
3. 明确告警检测、查询和重复告警处理语义；
4. 明确 MQTT 上下行接口边界；
5. 明确控制指令的成功 / 失败判定；
6. 明确 Modbus Server 首期需要暴露的数据；
7. 明确配置变更何时生效；
8. 明确离线、重试和恢复的业务要求；
9. 明确是否需要本地保存实时历史数据；
10. 明确首期可验收的性能和稳定性目标。

以上确认后，再进入技术方案设计和 Issue 拆分。
