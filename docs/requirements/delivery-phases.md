# Edge Collector 分阶段交付计划

> 状态：Active
>
> 本文定义 Edge Collector 的实施顺序。完整产品能力仍以 `edge-collector-requirements.md` 为准；本文只规定各阶段先做什么、暂不做什么，以及阶段验收闭环。

## 总体原则

Edge Collector 不一次性实现采集、告警、MQTT、控制、Modbus Server 等全部能力，而是按可独立运行、可独立验收的纵向闭环逐步推进。

每一阶段都应具备明确的可验证结果，不以“某个模块、接口或抽象已经写完”作为完成标准。

---

## 第一阶段：馈电保护器 RS485 采集 + 内存当前值 + 页面可视化

### 目标

第一阶段只建立最基础、最重要的数据链路：

```text
馈电保护器
  ↓
RS485 + Modbus RTU
  ↓
持续采集
  ↓
解析设备实时数据
  ↓
进程内存保存当前值
  ↓
后端查询接口
  ↓
React 管理页面查看当前数据
```

第一阶段的核心目标不是对接上级平台，而是证明 Edge Collector 自身已经能够稳定完成馈电保护器实时数据采集，并能够在管理页面直接看到最新采集结果。

第一阶段首先在开发机完成，不要求 RK3568 实机作为本阶段完成条件。

### 第一阶段必须完成

#### 1. RS485 通信通道配置

能够从页面配置实际采集所需的 RS485 串口参数，例如：

- 串口设备；
- 波特率；
- 数据位；
- 停止位；
- 校验方式；
- 通信超时等必要参数。

第一阶段不要求 TCP、UDP 接入。它们仍属于完整产品能力，后续阶段再实现和验证。

#### 2. 设备配置

能够保存并管理采集所需的基础设备信息，包括：

- 设备唯一标识；
- 设备名称；
- 设备类型；
- 所属 RS485 通信通道；
- Modbus 地址；
- 是否启用；
- 采集周期。

首个设备类型固定为**馈电保护器**。馈电保护器的寄存器地址、功能码、数据类型 / 字节序、比例系数和状态位等解析规则由代码内置，第一阶段不提供用户自定义寄存器表功能。

设备和通信配置保存到 SQLite。通信通道和采集设备配置在数据库事务提交成功后刷新到运行中的采集器；物理串口参数在当前设备采集完成后的通道边界重建会话，调度参数在后续请求中生效。详见 [ADR-0013](../adr/0013-rs485-request-pacing-and-runtime-reconfiguration.md) 和 [RS485 采集报文节流与配置运行时刷新 Spec](../specs/rs485-acquisition-pacing-and-runtime-reconfiguration.md)。

#### 3. 持续实时采集

启用后的馈电保护器必须按照配置持续轮询，而不是只执行一次读取。

要求：

- 能够按照馈电保护器协议读取并解析实时数据；
- 单次通信失败后后续采集仍可继续；
- 单个设备异常不能导致其他设备长期停止采集；
- 同一路 RS485 上的通信不能发生报文冲突；
- 开发顺序允许先单设备跑通，再扩展同总线多设备。

#### 4. 当前数据保存到内存

第一阶段采集得到的实时数据以“当前值”为核心，保存在进程内存中。

每个设备的当前状态至少应能够表达：

- 当前实时数据；
- 最近一次成功采集时间；
- 最近一次采集尝试时间；
- 当前通信状态；
- 最近一次通信异常信息（如有）。

如果一次采集包含多个寄存器区域，部分成功、部分失败，允许更新成功的数据；失败数据可保留上一次有效值，但必须保留新鲜度 / 有效性信息，不能把旧值误认为本轮新值。

第一阶段不把每次实时采集值写入 SQLite，也不建设历史时序数据库。

程序重启后内存实时值允许丢失；服务根据持久化设备配置重新开始采集后，应重新形成当前值。

#### 5. 基本通信状态

第一阶段需要支持页面可见的基本设备通信状态：

- 单次失败记录通信失败；
- 默认连续 3 次失败后判离线；
- 连续失败阈值和通信超时允许配置；
- 后续任意一次成功通信即可恢复在线。

#### 6. 后端查询能力

管理后台需要能够查询当前采集状态和实时值。

需求只规定“页面能够取得当前数据”，不在本阶段提前固定内部缓存结构或 API 内部实现。

#### 7. 页面实时数据查看

React 管理后台采用“设备列表 + 当前数据详情”的基本形态。

设备列表至少展示：

- 设备名称 / 标识；
- 所属通信通道；
- Modbus 地址；
- 当前通信状态；
- 最近更新时间。

设备详情展示馈电保护器当前实时数据以及必要的有效性 / 错误信息。

第一阶段页面使用 HTTP 定时轮询后端当前状态接口实现持续刷新，不要求 SSE 或 WebSocket。具体轮询间隔由技术设计确定。

### 第一阶段明确不做

以下能力属于完整产品需求，但不进入第一阶段交付范围：

- TCP / UDP 设备接入；
- 高开保护器协议适配；
- MQTT Client 接入；
- 实时数据 MQTT 上报；
- MQTT 控制指令订阅；
- 远程设备控制；
- 告警触发、告警详情查询与告警上报；
- Modbus Server 对外服务；
- 高频实时历史数据持久化；
- 历史曲线 / 时序查询；
- MQTT、告警、控制等后续业务配置的热加载；采集通道和采集设备配置的运行时刷新按 ADR-0013 执行；
- 复杂优先级调度；
- 用户可配置寄存器表；
- 通用插件系统或动态脚本系统；
- RK3568 实机作为本阶段验收条件。

这些能力不得成为第一阶段采集闭环的前置依赖。

### 第一阶段验收口径

第一阶段完成应至少满足：

1. Edge Collector 可以在开发机正常运行；
2. SQLite 能保存 RS485 通信通道和设备配置；
3. 能按照已有馈电保护器 Modbus RTU 协议持续采集并解析实时数据；
4. 采集结果能够更新到进程内存中的当前状态；
5. 后端接口能够读取当前设备状态和实时数据；
6. React 页面能够通过 HTTP 定时刷新持续看到最新采集值及更新时间；
7. 页面能够看到设备当前通信状态和必要错误信息；
8. 默认连续 3 次失败后设备显示离线，后续采集成功后恢复在线；
9. 部分寄存器区域读取失败时，成功数据仍可更新，失败数据不会被伪装成新数据；
10. 至少验证同一路 RS485 上 2 台或以上同类设备通过不同 Modbus 地址持续轮询；
11. 单台设备超时 / 离线不会让其他设备永久停止采集；
12. 服务重启后可从 SQLite 恢复配置并重新形成内存当前值；
13. 第一阶段运行不依赖 MQTT Broker、告警链路或 Modbus Server；
14. 第一阶段不要求在 RK3568 实机完成。

---

## 第二阶段：告警采集与设备状态完善

在第一阶段稳定后，再加入：

- 告警状态持续轮询；
- 告警触发后的详情查询；
- 告警去重 / 重复告警规则；
- 更完整的设备在线、离线、恢复状态；
- 页面告警与通信状态展示；
- 告警与普通实时采集竞争同一通道时的协调规则。

第二阶段仍可以不依赖 MQTT，先在本地完成告警采集闭环。

---

## 第三阶段：MQTT 上下行与远程控制

在本地采集和告警链路稳定后，再接入上级平台：

- MQTT Client 连接；
- 实时数据上报；
- 告警上报；
- 设备状态上报；
- MQTT 控制指令订阅；
- 设备控制执行；
- 控制结果反馈；
- MQTT 断线重连及必要的消息可靠性策略。

这一阶段再正式确定 Topic、Payload、QoS、断线补发等接口约束。

---

## 第四阶段：Modbus Server 与生产化完善

最后补齐对外数据服务与生产运行能力：

- Modbus Server；
- 对外寄存器映射；
- 现场设备离线时的对外数据语义；
- 高开保护器及其他设备类型扩展；
- TCP / UDP 设备接入；
- 长期稳定性与压力测试；
- 资源占用与异常恢复优化；
- RK3568 正式部署流程；
- 根据实际项目需要补充历史数据，以及 MQTT、告警、控制等后续业务配置的热加载能力。

---

## 当前实施状态

当前正式进入 **第一阶段：馈电保护器 RS485 采集 + 内存当前值 + 页面可视化**。

现阶段的技术设计和 Issue 拆分均应围绕这一阶段展开。MQTT、告警、控制、Modbus Server、TCP / UDP 和 RK3568 部署细节暂不阻塞第一阶段开发。

第一阶段关键决策见 `docs/adr/0011-phase-one-rs485-modbus-rtu-acquisition.md`。
