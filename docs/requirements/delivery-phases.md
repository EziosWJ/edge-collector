# Edge Collector 分阶段交付计划

> 状态：Active
>
> 本文定义 Edge Collector 的实施顺序。完整产品能力仍以 `edge-collector-requirements.md` 为准；本文只规定各阶段先做什么、暂不做什么，以及阶段验收闭环。

## 总体原则

Edge Collector 不一次性实现采集、告警、MQTT、控制、Modbus Server 等全部能力，而是按可独立运行、可独立验收的纵向闭环逐步推进。

每一阶段都应具备明确的可验证结果，不以“某个模块、接口或抽象已经写完”作为完成标准。

---

## 第一阶段：馈电保护器 RS485 原始寄存器采集 + 内存当前状态 + 页面可视化

### 目标

第一阶段只建立最基础、最重要的数据链路：

```text
馈电保护器
  ↓
RS485 + Modbus RTU
  ↓
持续采集
  ↓
按配置读取 FC03 / FC04 原始寄存器
  ↓
进程内存保存寄存器当前快照
  ↓
后端查询接口
  ↓
React 管理页面查看实时寄存器
```

第一阶段的核心目标不是对接上级平台或解释厂家协议，而是证明 Edge Collector 能够稳定读取真实设备的原始寄存器，并在管理页面观察最新值、有效性和通信状态。

第一阶段首先在开发机完成，不要求 RK3568 实机作为本阶段完成条件。

### 第一阶段必须完成

#### 1. RS485 通信通道配置

能够从页面配置实际采集所需的 RS485 串口参数，例如：

- 串口设备；
- 波特率；
- 数据位；
- 停止位；
- 校验方式；
- 通信超时等必要参数。

第一阶段不要求 TCP、UDP 接入。它们仍属于完整产品能力，后续阶段再实现和验证。

#### 2. 设备配置

能够保存并管理采集所需的基础设备信息，包括：

- 设备唯一标识；
- 设备名称；
- 设备类型；
- 所属 RS485 通信通道；
- Modbus 地址；
- 是否启用；
- 采集周期；
- 一个或多个寄存器读取块。

首个设备类型固定为**馈电保护器**，但设备类型不参与第一阶段的读取分派。每个寄存器读取块配置同设备内唯一名称、FC03 或 FC04、零基起始地址、`1～125` 个寄存器和排序号；同一设备、同一功能码的读取块不得重叠。读取块不配置业务字段、数据类型、字节序、倍率、单位或状态位语义。

设备、读取块和通信配置保存到数据库。配置在数据库事务提交成功后刷新到运行中的采集器；物理串口参数在当前设备采集完成后的通道边界重建会话，调度参数和读取块在后续请求中生效。详见 [ADR-0013](../adr/0013-rs485-request-pacing-and-runtime-reconfiguration.md)、[ADR-0014](../adr/0014-raw-register-acquisition-before-protocol-parsing.md) 和 [RS485 采集报文节流与配置运行时刷新 Spec](../specs/rs485-acquisition-pacing-and-runtime-reconfiguration.md)。

#### 3. 持续实时采集

启用后的馈电保护器必须按照配置持续轮询，而不是只执行一次读取。

要求：

- 能够按设备配置的有序读取块持续读取 FC03 / FC04 原始寄存器；
- 每个寄存器只作为 16-bit 无符号值保存，不进行有符号数、浮点数、多寄存器组合、比例、单位或状态位解释；
- 单次通信失败后后续采集仍可继续；
- 单个读取块失败后，该设备的后续读取块仍可继续；
- 单个设备异常不能导致其他设备长期停止采集；
- 同一路 RS485 上的通信不能发生报文冲突；
- 开发顺序允许先单设备跑通，再扩展同总线多设备。

#### 4. 当前数据保存到内存

第一阶段采集得到的原始寄存器数据以“当前快照”为核心，保存在进程内存中。

每个设备的当前状态至少应能够表达：

- 按读取块组织的寄存器地址和当前 16-bit 无符号值；
- 每个读取块的本轮有效性；
- 最近一次成功采集时间；
- 最近一次采集尝试时间；
- 当前通信状态；
- 最近一次通信异常信息（如有）。

读取块首次成功前也展示配置的地址，值为空。读取块成功时，该块全部寄存器作为同一批次更新；失败时保留上一次成功值，但整块标记为本轮无效，不能把旧值误认为本轮新值。第一阶段不保存历史批次。

第一阶段不把每次实时采集值写入 SQLite，也不建设历史时序数据库。

程序重启后内存实时值允许丢失；服务根据持久化设备配置重新开始采集后，应重新形成当前值。

#### 5. 基本通信状态

第一阶段需要支持页面可见的基本设备通信状态：

- 所有读取块成功时为在线；
- 部分读取块成功、部分失败时为近期失败 / 降级；
- 所有读取块连续失败达到阈值后判离线，任一读取块成功都会中断该连续计数；
- 连续失败阈值和通信超时允许配置；
- 后续一个完整采集周期内所有读取块成功后恢复在线。

#### 6. 后端查询能力

管理后台需要能够通过 `/api/v1/acquisition/states` 查询设备通信状态和 `registerBlocks` 原始寄存器快照。

需求只规定“页面能够取得当前数据”，不在本阶段提前固定内部缓存结构或 API 内部实现。

#### 7. 页面实时寄存器查看

React 管理后台采用“设备列表 + 当前数据详情”的基本形态。

设备列表至少展示：

- 设备名称 / 标识；
- 所属通信通道；
- Modbus 地址；
- 当前通信状态；
- 最近更新时间。

页面名称为“实时寄存器”。设备详情按读取块展示读取块名称、功能码、零基十进制地址、当前值、本轮有效性、最后成功时间、最近尝试时间和错误。

寄存器值默认显示为四位 HEX，允许页面级全局切换为无符号 DEC 或 16 位 BIN。切换只改变同一个 16-bit 值的文本表示，不改变地址和 API 数据。

第一阶段页面使用 HTTP 定时轮询后端当前状态接口实现持续刷新，不要求 SSE 或 WebSocket。具体轮询间隔由技术设计确定。

### 第一阶段明确不做

以下能力属于完整产品需求，但不进入第一阶段交付范围：

- TCP / UDP 设备接入（已由 ADR-0015 建立；本阶段说明不覆盖其后续生产化压力验证）；
- 高开保护器协议适配；
- MQTT Client 接入；
- 实时数据 MQTT 上报；
- MQTT 控制指令订阅；
- 远程设备控制；
- 告警触发、告警详情查询与告警上报；
- Modbus Server 对外服务；
- 高频实时历史数据持久化；
- 历史曲线 / 时序查询；
- MQTT、告警、控制等后续业务配置的热加载；采集通道、设备和读取块配置的运行时刷新按 ADR-0013、ADR-0014 执行；
- 复杂优先级调度；
- 设备协议解析，包括有符号数、浮点数、多寄存器组合、字节序 / 字序、比例、单位和状态位语义；
- 用户可配置业务字段或协议映射的通用寄存器解释器；
- 通用插件系统或动态脚本系统；
- RK3568 实机作为本阶段验收条件。

这些能力不得成为第一阶段采集闭环的前置依赖。

### 第一阶段验收口径

第一阶段完成应至少满足：

1. Edge Collector 可以在开发机正常运行；
2. PostgreSQL 和 SQLite 能保存 RS485 通信通道、设备和多个有序寄存器读取块；
3. 同一 RS485 通道至少有两台启用设备通过不同 Modbus 地址持续轮询；
4. 单台设备可以配置多个 FC03 / FC04 读取块，且同一功能码下拒绝重叠地址；
5. 原始寄存器结果能够按读取块和零基地址更新到进程内存当前状态；
6. `/api/v1/acquisition/states` 能返回设备通信状态和 `registerBlocks`；
7. “实时寄存器”页面通过 HTTP 定时刷新，并能在 HEX / DEC / BIN 间切换同一原始值；
8. 单个读取块失败时其他块继续更新，失败块保留旧值但标记无效，设备显示降级；
9. 所有读取块连续失败达到阈值后设备显示离线，任一读取块恢复成功后退出全部失败状态；
10. 新增、修改或删除读取块后运行时热生效；名称 / 排序变化保留快照，读取范围变化清除旧快照；
11. 单台设备超时 / 离线不会让同通道其他设备永久停止采集；
12. 服务重启后可从数据库恢复配置并重新形成内存当前状态；
13. 页面、API 和主采集链路不出现电压、单位、倍率或其他未经厂家协议确认的解析结果；
14. 第一阶段运行不依赖 MQTT Broker、告警链路、Modbus Server 或 RK3568 实机。

---

## 第二阶段：告警采集与设备状态完善

在第一阶段稳定后，再加入：

- 告警状态持续轮询；
- 告警触发后的详情查询；
- 告警去重 / 重复告警规则；
- 更完整的设备在线、离线、恢复状态；
- 页面告警与通信状态展示；
- 告警与普通实时采集竞争同一通道时的协调规则。

第二阶段仍可以不依赖 MQTT，先在本地完成告警采集闭环。

---

## 第三阶段：MQTT 上下行与远程控制

在本地采集和告警链路稳定后，再接入上级平台：

- MQTT Client 连接；
- 实时数据上报；
- 告警上报；
- 设备状态上报；
- MQTT 控制指令订阅；
- 设备控制执行；
- 控制结果反馈；
- MQTT 断线重连及必要的消息可靠性策略。

第三阶段的接口约束已经由 ADR-0017 固定并完成实现：第一版使用单逻辑 Broker、默认 MQTT 5 且保持 MQTT 3.1.1 应用层兼容；固定 raw/status/event/command/command-result Topic/Payload v1、QoS/retain、latest-state raw、bounded reliable outbox、command journal 和 Starlark `command(ctx,name,args)` safe-boundary 控制语义。实现对应 GitHub Spec #39 及 #40～#47；真实 Docker Broker/PostgreSQL 验收记录见 `docs/acceptance/adr-0017-mqtt-reliable-control.md`。

---

## 第四阶段：Modbus Server 与生产化完善

最后补齐对外数据服务与生产运行能力：

- Modbus Server；
- 对外寄存器映射；
- 现场设备离线时的对外数据语义；
- 高开保护器及其他设备类型扩展；
- TCP / UDP 设备接入；
- 长期稳定性与压力测试；
- 资源占用与异常恢复优化；
- RK3568 正式部署流程；
- 根据实际项目需要补充历史数据，以及 MQTT、告警、控制等后续业务配置的热加载能力。

---

## 当前实施状态

第一阶段的馈电保护器 RS485 原始寄存器采集、内存当前状态和页面可视化已完成；ADR-0015 进一步完成了 `MODBUS_RTU`、`MODBUS_TCP`、`MODBUS_UDP` 与 `MODBUS_RTU_OVER_UDP` 的统一 raw 采集底座。

当前已确认交付的采集能力还包括 ADR-0016 用户可配置 Starlark 动态事务：脚本 draft、Validate、不可变 Publish/Rollback、设备绑定、`after_poll(ctx)`、受控 FC03/FC16/FC05、delay、state/event overlay 以及独立运行观察。固定 `registerBlocks` 仍负责基础采集，脚本不接管 transport、session 或 channel 调度。

ADR-0017 已完成 MQTT 第三阶段的架构、Implementation Spec 和 #40～#47 实现；MQTT Client、raw/status/event 实际上报、reliable outbox、command journal、Starlark `command(ctx,name,args)`、远程控制和 MQTT 管理页面已交付。真实 Broker、PostgreSQL、MQTT 5/3.1.1 全矩阵需要 Docker daemon，当前执行环境的阻塞项记录在验收文档中。

后续仍需正式业务告警模型与历史、`telemetry`/`alarm` 业务语义、Modbus Server、工程量解析以及生产化压力和 RK3568 部署完善。ADR-0016 dynamic event 不等同于业务告警；ADR-0017 第一版 raw/event 也不等同于正式 telemetry/alarm domain。

第一阶段关键决策见 `docs/adr/0011-phase-one-rs485-modbus-rtu-acquisition.md`、`docs/adr/0013-rs485-request-pacing-and-runtime-reconfiguration.md` 和 `docs/adr/0014-raw-register-acquisition-before-protocol-parsing.md`；四传输底座见 `docs/adr/0015-multi-transport-modbus-channels-and-network-device-addressing.md`，动态事务见 `docs/adr/0016-user-configurable-starlark-modbus-dynamic-transactions.md`，MQTT 上下行设计见 `docs/adr/0017-mqtt-uplink-downlink-reliable-control.md` 与 `docs/specs/mqtt-uplink-downlink-reliable-control.md`。
