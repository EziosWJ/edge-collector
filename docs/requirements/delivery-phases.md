# Edge Collector 分阶段交付计划

> 状态：Active
>
> 本文定义 Edge Collector 的实施顺序。完整产品能力仍以 `edge-collector-requirements.md` 为准；本文只规定各阶段先做什么、暂不做什么，以及阶段验收闭环。

## 总体原则

Edge Collector 不一次性实现采集、告警、MQTT、控制、Modbus Server 等全部能力，而是按可独立运行、可独立验收的纵向闭环逐步推进。

每一阶段都应具备明确的现场可验证结果，不以“某个模块、接口或抽象已经写完”作为完成标准。

---

## 第一阶段：设备采集 + 内存当前值 + 页面可视化

### 目标

第一阶段只建立最基础、最重要的数据链路：

```text
现场设备
  ↓
RS485 / TCP / UDP
  ↓
Modbus 采集
  ↓
解析设备实时数据
  ↓
进程内存保存当前值
  ↓
后端查询接口
  ↓
React 管理页面查看当前数据
```

第一阶段的核心目标不是对接上级平台，而是证明 Edge Collector 自身已经能够稳定完成现场设备数据采集，并能够在管理页面直接看到最新采集结果。

### 第一阶段必须完成

#### 1. 通信通道配置

能够配置实际采集所需的通信参数，包括：

- RS485 串口参数；
- TCP 参数；
- UDP 参数。

首个实际验收可以优先使用真实 RS485 Modbus 设备，不要求第一阶段同时把所有通信方式都做到同等验证深度。

#### 2. 设备配置

能够保存并管理采集所需的基础设备信息，例如：

- 设备唯一标识；
- 设备名称；
- 设备类型 / 型号；
- 所属通信通道；
- Modbus 地址；
- 是否启用；
- 采集周期及必要通信参数。

设备和通信配置可以保存到 SQLite；具体表结构由后续技术设计决定。

#### 3. 持续实时采集

启用后的设备必须按照配置持续轮询，而不是只执行一次读取。

要求：

- 能够读取真实设备实时数据；
- 能够按照具体设备协议解析数据；
- 单次通信失败后后续采集仍可继续；
- 单个设备异常不能导致其他设备长期停止采集；
- 同一路 RS485 上的通信不能发生报文冲突；
- 不同独立通信通道应能够正常工作。

#### 4. 当前数据保存到内存

第一阶段采集得到的实时数据以“当前值”为核心，保存在进程内存中。

内存中的当前状态至少应能够表达：

- 当前采集值；
- 数据对应的设备；
- 最近一次成功采集时间；
- 当前通信状态；
- 必要的最近通信异常信息。

第一阶段不要求把每次实时采集值写入 SQLite，也不建设历史时序数据库。

程序重启后内存实时值允许丢失；服务根据持久化设备配置重新开始采集后，应重新形成当前值。

#### 5. 后端查询能力

管理后台需要能够查询当前采集状态和实时值。

需求只规定“页面能够取得当前数据”，不在此阶段提前固定内部缓存结构，也不强制规定页面必须使用轮询、SSE、WebSocket 或其他刷新机制。

#### 6. 页面实时数据查看

React 管理后台需要提供面向采集业务的查看页面。

第一阶段页面至少应能够看到：

- 已配置设备；
- 设备当前在线 / 通信状态；
- 设备最新实时数据；
- 最新数据更新时间；
- 采集失败时必要的状态提示。

页面目标是用于开发、联调和现场验证，不要求第一阶段完成复杂大屏、趋势图、历史曲线或高级可视化。

### 第一阶段明确不做

以下能力属于完整产品需求，但不进入第一阶段交付范围：

- MQTT Client 接入；
- 实时数据 MQTT 上报；
- MQTT 控制指令订阅；
- 远程设备控制；
- 告警触发、告警详情查询与告警上报；
- Modbus Server 对外服务；
- 高频实时历史数据持久化；
- 历史曲线 / 时序查询；
- 所有配置的热加载；
- 复杂优先级调度；
- 通用插件系统或动态脚本系统。

这些能力不得成为第一阶段采集闭环的前置依赖。

### 第一阶段验收口径

第一阶段完成应至少满足：

1. Edge Collector 可以在开发环境正常运行；
2. SQLite 能保存设备和通信相关配置；
3. 至少接入 1 类真实 Modbus 设备并持续采集；
4. 至少验证 1 路 RS485 上多台同类设备能够持续轮询；
5. 采集结果能够更新到进程内存中的当前状态；
6. 后端接口能够读取当前设备状态和实时数据；
7. React 页面能够持续看到最新采集值及更新时间；
8. 单台设备断线 / 超时不会让其他设备的采集永久停止；
9. 服务重启后可从持久化配置恢复采集，并重新形成内存当前值；
10. 第一阶段运行不依赖 MQTT Broker 或 Modbus Server。

如果实际首期设备只有单台，也可以先完成单设备闭环，再补同总线多设备验收；但第一阶段最终仍需要验证同一路 RS485 多设备场景。

---

## 第二阶段：告警采集与设备状态完善

在第一阶段稳定后，再加入：

- 告警状态持续轮询；
- 告警触发后的详情查询；
- 告警去重 / 重复告警规则；
- 更完整的设备在线、离线、恢复状态；
- 页面告警与通信状态展示；
- 告警与普通实时采集竞争同一通道时的协调规则。

第二阶段仍可以不依赖 MQTT，先在本地完成告警采集闭环。

---

## 第三阶段：MQTT 上下行与远程控制

在本地采集和告警链路稳定后，再接入上级平台：

- MQTT Client 连接；
- 实时数据上报；
- 告警上报；
- 设备状态上报；
- MQTT 控制指令订阅；
- 设备控制执行；
- 控制结果反馈；
- MQTT 断线重连及必要的消息可靠性策略。

这一阶段再正式确定 Topic、Payload、QoS、断线补发等接口约束。

---

## 第四阶段：Modbus Server 与生产化完善

最后补齐对外数据服务与生产运行能力：

- Modbus Server；
- 对外寄存器映射；
- 现场设备离线时的对外数据语义；
- 长期稳定性与压力测试；
- 资源占用与异常恢复优化；
- RK3568 正式部署流程；
- 根据实际项目需要补充历史数据、配置热加载等能力。

---

## 当前实施状态

当前正式进入 **第一阶段：设备采集 + 内存当前值 + 页面可视化**。

现阶段的需求评审、技术设计和 Issue 拆分均应优先围绕这一阶段展开。MQTT、告警、控制和 Modbus Server 的细节问题暂不阻塞第一阶段开发。
