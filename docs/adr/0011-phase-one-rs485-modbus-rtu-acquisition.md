# ADR-0011: 第一阶段采用 RS485 Modbus RTU 采集闭环与内存当前状态

## Status

Accepted

## Context

Edge Collector 的完整产品目标包括现场设备采集、告警、MQTT 上下行、远程控制、Modbus Server 和生产化部署。为避免在项目早期同时展开过多链路，第一阶段需要先形成一个可独立运行、可独立验收的最小采集闭环。

经过需求 Grill，第一阶段的首个协议对象确定为**馈电保护器**，通信方式为 **RS485 + Modbus RTU**。馈电保护器的寄存器地址、功能码、数据类型 / 字节序、比例系数和状态位定义等协议资料已经具备。

完整产品仍保留高开保护器、TCP、UDP、MQTT、告警、控制和 Modbus Server 等需求，但这些能力不进入第一阶段验收范围。

## Decision

### 1. 第一阶段只要求 RS485 + Modbus RTU

第一阶段以馈电保护器为首个真实设备类型，优先完成 RS485 Modbus RTU 采集闭环。

TCP、UDP 以及其他传输方式保留在完整产品需求中，但不作为第一阶段验收条件，也不得为了提前统一这些传输方式而延迟首个 RS485 采集闭环。

高开保护器属于后续需要支持的设备类型，不要求与馈电保护器同时进入第一阶段首个实现。

### 2. 第一阶段先在开发机完成

第一阶段的开发和验收首先在开发机完成，不要求以 RK3568 实机作为本阶段完成条件。

RK3568、Buildroot / Ubuntu 的真实部署仍是后续生产化目标；已有 SQLite + CGO ARM64 静态交叉编译验证继续有效，但不成为当前采集功能开发的前置工作。

### 3. 设备协议规则由代码内置

第一阶段不建设“用户可配置寄存器表”的通用协议配置器。

馈电保护器的寄存器地址、数据类型、字节序、比例系数、状态位解析等规则由代码中的设备类型适配逻辑实现。管理页面只允许选择设备类型并配置运行所需参数，例如：

- 通信通道；
- 串口参数；
- Modbus 地址；
- 是否启用；
- 采集周期。

后续增加高开保护器等设备类型时，应新增对应的协议适配能力，而不是要求用户在页面手工录入寄存器解析规则。

本 ADR 不规定该适配能力最终使用何种 Driver interface、目录结构或函数签名。

### 4. 设备与通信配置持久化到 SQLite

第一阶段需要能够从管理页面维护通信通道与设备配置，并将配置持久化到 SQLite。

第一版允许配置保存后通过重启服务生效，不要求所有采集配置热加载。页面应明确提示需要重启生效的配置变更。

### 5. 实时采集结果只保存“当前状态”到进程内存

第一阶段不把每轮实时采集结果写入 SQLite，也不建设历史时序数据库。

每个设备的当前状态至少应能够表达：

- 最新实时数据；
- 最近一次成功采集时间；
- 最近一次采集尝试时间；
- 当前通信状态；
- 最近一次通信异常信息（如有）。

进程重启后这些实时值允许丢失；服务根据 SQLite 中的持久化配置重新开始采集后，再重新形成当前状态。

本 ADR 只规定这些业务语义，不规定内存使用 map、cache、store 或其他具体数据结构。

### 6. 部分读取失败不使整台设备的成功数据全部失效

如果一次设备采集包含多个寄存器区域，部分区域读取成功、部分区域失败：

- 已成功解析的数据允许更新当前状态；
- 失败数据允许保留上一次有效值；
- 必须能够区分数据的新鲜度 / 有效性，避免旧值被误认为本轮新值；
- 本轮存在部分失败时，应保留可用于页面诊断的错误信息。

### 7. 页面采用“设备列表 + 当前数据详情”

第一阶段页面用于开发、联调和现场验证，不建设大屏、历史曲线或高级可视化。

设备列表至少展示：

- 设备名称 / 标识；
- 所属通信通道；
- Modbus 地址；
- 当前通信状态；
- 最近更新时间。

设备详情展示该设备当前实时数据及必要的有效性 / 错误信息。

页面通过 HTTP 定时轮询后端当前状态接口实现持续刷新。具体轮询间隔由技术设计确定，本 ADR 不锁定固定秒数。

### 8. 基本离线判定采用连续失败次数

第一阶段默认：

- 单次通信失败记录失败状态，但不立即判定长期离线；
- 连续 3 次失败后判定设备离线；
- 连续失败阈值和通信超时允许配置；
- 后续任意一次成功通信即可恢复在线状态。

### 9. 第一阶段最终需要验证同一路 RS485 多设备

开发顺序允许先跑通单台馈电保护器，再增加同一路 RS485 上的多台同类设备。

第一阶段最终验收需要至少验证同一路 RS485 上 2 台或以上同类设备，通过不同 Modbus 地址持续轮询，并确保单台设备异常不会让其他设备永久停止采集。

### 10. 第一阶段明确不包含后续业务能力

以下能力不进入第一阶段：

- MQTT Client；
- 实时数据 MQTT 上报；
- MQTT 控制；
- 远程设备控制；
- 告警状态轮询和告警详情采集；
- Modbus Server；
- 高频实时历史数据持久化；
- 历史曲线 / 时序查询；
- 所有配置热加载；
- 通用插件系统或动态脚本系统。

## Consequences

- 第一阶段可以集中验证最关键的现场采集链路，减少 MQTT、告警和控制等外部依赖对开发节奏的影响。
- 协议规则内置代码使首个设备实现更直接，但增加新设备类型时仍需开发和发布代码。
- 实时值只保存在内存中，进程重启后不会保留历史采集结果；这符合第一阶段“当前状态”定位。
- 采用 HTTP 轮询可以降低前端实时推送实现复杂度，后续如有必要可再升级为 SSE 或 WebSocket。
- 允许保存后重启生效，避免第一阶段提前引入运行时动态重配置复杂度。
- 第一阶段不要求 RK3568 实机完成，因此开发闭环可以更快完成；后续仍需要单独进行 ARM64 / 现场硬件验证。

## Deferred Decisions

以下内容留到后续技术设计或对应阶段再决定：

- 设备协议适配的具体 Go interface / struct / package 组织；
- goroutine、worker、队列或事件循环模型；
- 同一路串口事务协调的具体实现；
- 内存当前状态的具体数据结构；
- HTTP API 的最终路径和 DTO；
- 页面轮询的最终间隔；
- TCP / UDP 设备接入；
- 高开保护器协议适配；
- 告警、MQTT、控制和 Modbus Server 设计。
