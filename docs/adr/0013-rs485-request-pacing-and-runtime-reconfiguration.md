# ADR-0013: RS485 通道请求节流与采集配置运行时刷新

## Status

Accepted

## Context

第一阶段的采集运行时为每个启用的 RS485 通信通道维护一个 Modbus RTU 会话，并在该会话上串行轮询多个设备。一次设备采集可以包含多个有序寄存器读取块。底层 Modbus RTU 客户端已经保证协议要求的帧间静默，但现场设备还可能需要额外的设备处理时间。

现有设备的 `pollIntervalMs` 是设备级采集周期，控制同一设备再次采集的频率；它不能表达同一通道连续请求之间的业务等待。与此同时，管理配置如果只在进程启动时加载，会使通道和设备配置与实际运行采集不一致。

本 ADR supersede ADR-0011 中“配置保存后通过重启服务生效”以及“第一阶段不要求所有配置热加载”的采集配置部分；ADR-0014 进一步将运行时刷新范围扩展到寄存器读取块，并 supersede 本 ADR 中“两段固定电气量 / 状态读取”的采集假设。

## Decision

### 1. 通道增加报文间隔延迟

通信通道增加 `interRequestDelayMs` 配置，允许范围为 `0～60000` 毫秒，默认值为 `0`。

该字段表示同一通道上一条 Modbus 请求完成后、下一条 Modbus 请求发送前增加的业务等待时间。它适用于：

- 同一设备的连续寄存器读取块之间；
- 同一通道不同设备的读取之间；
- 后续接入该通道的其他 Modbus 请求。

`0` 只表示不增加业务延迟，不关闭底层 Modbus RTU 客户端自动保证的 `t3.5` 帧间静默。

通道打开后的第一条请求不增加业务延迟。底层协议库仍按其 RTU 实现处理协议需要的时序。

### 2. 保留设备级采集周期

`pollIntervalMs` 继续属于设备，而不是通道。一次设备采集完整结束后，运行时等待该设备的采集周期再安排下一次采集。

采集运行时遵循以下规则：

- 同一通道不并发发送请求；
- 不因设备读取超时而追赶或补发周期；
- 多个设备同时到期时，优先处理到期时间更早的设备，到期时间相同时按设备 ID 排序；
- 新增或重新启用的设备在下一次调度时立即进行首次采集；
- 报文间隔延迟导致实际刷新周期超过配置的采集周期时，允许实际周期自然变长，不自动修改配置；
- 失败请求同样遵守通道报文间隔延迟；单个读取块失败后继续处理该设备的后续读取块，使其他块仍有机会更新。

### 3. 以通道级 paced session 统一节流

报文间隔延迟由通道级的串行会话统一执行，而不是散落在某一种设备协议适配器中。这样当前轮询读取和未来控制指令可以共享同一个通道请求边界，避免后续能力绕过通道节流。

### 4. 采集配置运行时刷新

所有通信通道和采集设备的成功新增、修改、删除、启用、禁用和从站地址修改，都需要在数据库事务提交成功后通知采集运行时刷新。ADR-0014 新增的寄存器读取块写操作沿用同一刷新机制。数据库是最终配置来源；通知或应用失败不回滚已经提交的配置，运行时记录错误并持续按新配置重试。

运行时刷新遵循以下边界：

- 当前正在执行的设备采集必须先完成，不能中途切换会话或从站地址；
- 调度参数变化（报文间隔延迟、采集周期、启用状态）在当前请求完成后应用，不要求重建串口；
- 物理串口参数变化（端口、波特率、数据位、停止位、校验、通信超时）在通道边界关闭旧会话并重建；
- 新配置无法打开时停止使用旧会话，以新配置重试；
- 被禁用或删除的设备从当前状态集合中移除，不伪装成离线设备；
- 新配置仍然没有可用设备的通道不保持空闲串口会话。

配置写入接口只在数据库提交成功后返回成功；运行时应用失败通过采集日志体现，不改变已经持久化的配置结果。

### 5. 配置契约同步落地

`interRequestDelayMs` 必须同步存在于：

- PostgreSQL 和 SQLite 的 acquisition channel schema；
- Go 模型、输入校验、Repository 和 API DTO；
- React 通信通道表单、列表和类型定义；
- 运行时通道会话。

已有通道迁移后默认值为 `0`，缺省或显式传入 `0` 均表示不增加业务延迟。

## Considered Options

- **只增加设备间延迟**：不能覆盖同一设备连续读取块之间的处理时间，因此不选。
- **把 `pollIntervalMs` 改成通道整轮周期**：会使同一通道设备数量增加时单台设备刷新频率不可预测，因此不选。
- **把设备所有读取块合并为一条请求**：虽然能减少报文数量，但无法覆盖不连续地址和不同功能码，也会破坏读取块级部分有效性语义，因此不选。
- **只在 API 重启后加载新配置**：实现简单，但会使管理配置和实际采集行为不一致，因此不选。
- **运行时周期性查询数据库**：能够发现外部数据库修改，但会引入持续查询和刷新时序复杂度；当前单 API 实例通过成功写操作通知运行时即可满足范围，因此不选。

## Consequences

- 同一通道的报文间隔可按现场设备需要配置，且不会覆盖 Modbus RTU 的底层协议间隔。
- `pollIntervalMs` 仍然表达单台设备的数据刷新频率，但串行总线拥塞或设备响应慢时，实际周期可能变长。
- 配置保存不再要求重启 API；运行时需要处理会话切换、重试和配置应用失败日志。
- 新增配置贯穿数据库、API、前端和运行时，PostgreSQL / SQLite migration 与契约测试必须同步维护。
- 当前状态只保留启用设备的实时集合，禁用或删除设备的内存当前状态会被移除。
