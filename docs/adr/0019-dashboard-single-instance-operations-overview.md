# Dashboard 定位为单实例只读运维概览

Edge Collector 管理后台的 Dashboard 定位为单个部署实例的只读运维概览，首要任务是让运维人员快速发现通信通道或设备异常，并进入专门页面继续排查。当前不建立项目切换或多实例聚合，不在 Dashboard 直接执行控制指令或配置变更，也不展示没有真实数据来源的泛化运营指标；这样可以匹配当前已确认的采集、设备状态和 MQTT 能力，避免虚构趋势或把高风险操作放进缺少完整权限与审计语义的入口。

## Considered Options

- 将 Dashboard 做成用户、日志、通知等后台模块的通用工作台：与当前产品核心的现场采集运维目标不一致。
- 现在引入项目模型并聚合多个现场实例：当前领域模型和数据来源尚未支持，增加跨实例边界与复杂度。
- 在 Dashboard 直接提供控制和配置操作：需要先明确操作权限、确认、幂等、审计和失败反馈，不作为本阶段首页职责。

## Consequences

- 首页设计优先围绕当前状态、通道/设备异常和排查跳转，不承诺长期趋势或业务运营指标。
- 首屏信息层级采用总体摘要、健康分域、异常项和排查入口；通信通道是采集运维对象的第一组织层级，设备状态作为进一步定位信息。
- 采集运行、设备通信、MQTT 上行、服务/数据库分别展示，不能用一个“系统正常/异常”状态替代它们。
- Dashboard 不计算或展示缺少可靠历史来源的系统可用率；汇总只表达各分域的当前状态和需要关注的数量。
- 未配置、等待首次采集、正常、部分失败、离线、数据获取失败和数据可能已过期必须保持可区分；获取失败不能被解释为设备离线，未知也不能被填充为零或正常。
- 用户无权访问的健康分域不展示、不请求其数据，也不计入当前用户可见的关注项汇总。
- 运维关注项覆盖服务/数据库未就绪、MQTT 连接或可靠 Outbox 风险、通道/设备部分失败或离线、协议脚本最近运行失败；未配置和等待首次采集只作为信息状态，动态事件、系统日志、站内通知和正式业务告警不直接混入该列表。
- 关注项按严重程度、再按持续时间排序，首屏最多展示 6 项并保留分类总数和查看全部入口；服务/数据库数据不可用优先于 MQTT 和采集对象的已知运行异常。
- Dashboard 采用现有浅色蓝灰企业后台体系，突出运行状态而非装饰性图表；关注项进入已有的实时寄存器、协议脚本或 MQTT 运行总览页面，不在首页复制详情模型或新建独立告警中心。
- 主体区域以通信通道状态板为主，展示通道运行状态和可定位的最近采集信息；Dashboard 不展示原始寄存器值，不把它们解释为电压、电流等业务实时数据，也不创建无历史来源的趋势图。
- 采集通道和设备健康使用当前状态摘要，不计算在线率、可用率、采集量或吞吐量；未配置对象单独表达。
- MQTT Outbox 沿用现有容量口径：利用率达到 80% 预警、达到 100% 严重，Raw pending 仅作为信息，不把任意 pending 直接当作故障。
- 页面和导航名称使用“运维概览”，避免与 MQTT 的“运行总览”混淆；通信通道状态板展示全部已启用通道并将关注项置顶，禁用通道不计入运行健康。
- 空态、等待首次采集、无关注项、首次请求失败和刷新后数据过期必须分别表达，并在用户有权限时提供进入配置或排查页面的入口。
- 桌面端采用关注项/通道主区域与健康分域摘要辅助区域的两栏布局；移动端按摘要、关注项、通道、MQTT/服务的顺序单列展示。
- 通道数量增长时仍保留全部已启用通道，关注项置顶，状态板在首屏内滚动并提供进入通信通道页的查看全部入口，不在 Dashboard 内分页。
- 页面可见时自动刷新当前状态，默认间隔约 10 秒，同时提供手动刷新、最近刷新时间和加载/错误状态。
- 没有真实数据来源的指标必须显示为未接入或暂无数据，而不是继续沿用脚手架占位数值。
- 后续若要支持多项目、多实例聚合或首页控制操作，需要重新评估并更新本决策。
