# 第一阶段技术方案：馈电保护器 RS485 Modbus RTU 采集闭环

> 状态：Accepted for implementation
>
> 范围基线：Issue #1 + ADR-0011。
>
> 本文进入技术方案层：决定模块职责、运行拓扑、依赖与数据流；除非实现验证证明必要，不在此处固定大量函数签名和细粒度接口。

## 1. 目标与非目标

第一阶段只实现：

```text
馈电保护器
  ↓
RS485 + Modbus RTU
  ↓
持续采集 / 解析
  ↓
进程内存当前状态
  ↓
HTTP 查询
  ↓
React 页面轮询展示
```

配置保存到 SQLite；实时采集结果不逐轮写入数据库。

第一阶段不实现 MQTT、告警、高开保护器、TCP/UDP、远程控制、Modbus Server、历史时序存储、SSE/WebSocket、通用寄存器配置器和通用插件平台。

## 2. 与现有工程的集成方式

现有项目继续保持模块化单体。

- `cmd/api` 继续作为 composition root，创建数据库、业务服务、采集运行时和 HTTP Server，并负责统一启动 / 停止。
- `internal/app` 继续负责 Gin 路由装配，不承载采集循环。
- 新增采集领域模块，不创建独立进程或微服务。
- React 管理后台继续沿用现有显式路由和 API Client 组织方式。

采集运行时是与 HTTP Server 并列的后台能力，而不是由某个 HTTP 请求触发的临时任务。

## 3. 后端模块边界

第一阶段建议建立一个明确的 `acquisition` 业务边界，避免一开始拆成大量抽象层。

建议职责：

```text
internal/acquisition
├─ 持久配置
│  ├─ RS485 通信通道
│  └─ 设备配置
├─ 当前状态
│  └─ 进程内存中的设备实时状态
├─ 采集运行时
│  ├─ 加载启用配置
│  ├─ 按通信通道组织设备
│  ├─ 周期性执行采集
│  └─ 更新当前状态
├─ 馈电保护器协议适配
│  └─ 原始 Modbus 寄存器 → 业务数据
└─ HTTP
   ├─ 配置管理
   └─ 当前状态查询
```

如实现过程中代码量增大，可在 `internal/acquisition` 下按 `transport`、`protocol`、`runtime` 等职责形成子包；第一批 Ticket 不为了目录形式先创建空抽象。

## 4. 持久数据模型

第一阶段新增两类持久配置。

### 4.1 RS485 通信通道

至少表达：

- 唯一 ID；
- 名称；
- 串口设备路径 / 端口名；
- 波特率；
- 数据位；
- 停止位；
- 校验方式；
- 通信超时；
- 是否启用；
- 创建 / 更新时间等已有项目通用字段。

### 4.2 设备

至少表达：

- 唯一 ID；
- 名称；
- 设备类型；
- 所属通信通道；
- Modbus Slave 地址；
- 采集周期；
- 连续失败离线阈值，默认 3；
- 是否启用；
- 创建 / 更新时间等已有项目通用字段。

第一阶段设备类型只实现 `馈电保护器`，但数据库字段应能表达设备类型，避免未来增加高开保护器时修改设备主表的基本语义。

### 4.3 Migration

继续遵循项目现有 PostgreSQL / SQLite 双 migration 树、逻辑版本锁步规则。

当前 schema 版本为 7，第一阶段采集配置从下一逻辑版本继续演进。不得使用 GORM `AutoMigrate()` 替代 Goose migration。

## 5. Modbus 与串口依赖

第一阶段建议采用：

- `github.com/grid-x/modbus` 作为 Modbus RTU Client 实现；
- 不在业务层直接扩散第三方库类型；
- 在采集基础设施边界内封装串口会话和 Modbus 请求。

选择理由：

1. 支持 RTU / ASCII / TCP / UDP，后续传输方式扩展有余地，但第一阶段只启用 RTU；
2. 请求 API 支持 `context.Context`，便于控制超时和关闭；
3. 2026 年仍有针对串口链路恢复、PTY 测试及传输错误处理的持续维护；
4. 直接复用成熟 CRC、帧编解码和串口实现，避免自行实现 Modbus RTU 协议栈。

业务代码不得依赖其未来可能使用的 TCP/UDP 能力；本阶段只把它作为 RS485 Modbus RTU 基础设施。

## 6. 运行拓扑：按物理通信通道串行执行

RS485 是共享总线，同一物理串口上的 Modbus 事务必须串行。

第一阶段采用以下运行拓扑：

```text
Acquisition Runtime

RS485 Channel A
  └─ 单一串行采集循环
      ├─ Device 1
      ├─ Device 2
      └─ Device N

RS485 Channel B
  └─ 单一串行采集循环
      ├─ Device 1
      └─ Device N
```

核心原则：

- 同一路 RS485 任何时刻只执行一个 Modbus 事务序列；
- 不同物理串口独立运行，Channel A 的超时不能阻塞 Channel B；
- 同通道设备按各自采集周期获得执行机会；
- 单台设备超时结束后继续处理后续设备；
- 不为每个寄存器读取建立无界 goroutine；
- 第一阶段不引入全局 worker pool、消息队列或复杂优先级调度器。

具体使用 ticker、timer、最小堆或简单 next-due 调度可在实现 Ticket 中根据测试选择，但必须满足以上可观测语义。

## 7. 生命周期

采集运行时随 API 进程启动：

```text
加载应用配置
→ 打开数据库
→ 构建 acquisition 配置服务 / 当前状态存储
→ 从 SQLite 读取启用的 RS485 通道和设备
→ 启动 Acquisition Runtime
→ 启动 HTTP Server
```

停止时：

```text
收到 SIGINT / SIGTERM
→ 停止接受新的采集周期
→ 取消正在等待的采集上下文
→ 关闭串口资源
→ 停止 HTTP Server
→ 关闭数据库
```

采集运行时必须纳入现有 graceful shutdown，不允许后台 goroutine 在进程退出路径上失控。

第一阶段配置保存后允许重启生效，因此运行时无需订阅数据库配置变化。

## 8. 馈电保护器协议适配

馈电保护器协议资料已经具备。

第一阶段协议适配负责：

```text
Modbus 原始响应
→ 按寄存器定义组合数据
→ 字节序 / 字序转换
→ 数据类型转换
→ 比例系数换算
→ 状态位解析
→ 馈电保护器业务实时数据
```

寄存器地址、功能码、数据类型、比例和状态位由代码内置。

页面和数据库不保存用户自定义寄存器定义。

为了可测试，协议“解析”应能在不连接串口的情况下用固定原始寄存器样本进行单元测试；串口 / Modbus I/O 与纯解析逻辑不要混在一个不可测试的大函数中。

## 9. 当前状态模型

当前状态只存在于进程内存。

每台设备至少维护：

```text
Device Current State
├─ Device ID
├─ 当前业务数据
├─ 最近一次采集尝试时间
├─ 最近一次成功时间
├─ 通信状态
├─ 连续失败次数
└─ 最近错误信息
```

对于业务数据中的字段 / 数据组，还必须能够表达是否是本轮成功更新，或至少表达最后成功更新时间，从而满足“部分读取失败时不能把旧值伪装为新值”。

第一阶段当前状态存储的要求：

- 进程内并发安全；
- 读接口不能阻塞串口通信；
- 更新以设备为边界保持一致快照；
- 容量由已配置设备数决定，不允许随采集周期无限增长；
- 不保存历史序列。

本方案不强制 store 的具体 map / mutex / atomic.Value 结构，由实现根据 race test 与可读性决定。

## 10. 通信状态状态机

第一阶段不需要复杂设备健康模型，但应统一以下状态变化：

```text
启动 / 尚未成功采集
        ↓
成功通信 ─────────────→ ONLINE
        ↑                  │
        │                  │ 单次失败
        │                  ↓
        └──────────── DEGRADED / FAILED
                           │
                           │ 连续失败达到阈值（默认 3）
                           ↓
                        OFFLINE
```

任意后续成功通信将失败计数清零并恢复 `ONLINE`。

实际枚举名称可在实现中调整，但 API 和页面必须能区分：尚无数据、在线、近期失败、离线。

## 11. HTTP API 方案

第一阶段新增两类 HTTP 能力。

### 11.1 配置管理

提供 RS485 通道和设备的 CRUD，以项目现有认证 / 响应 / 审计模式接入。

建议新业务 API 使用 `/api/v1/...`，不继续把采集领域塞进 `/api/system`。

具体路由名称由实现确定，但建议资源语义保持：

```text
/api/v1/acquisition/channels
/api/v1/acquisition/devices
```

### 11.2 当前状态查询

提供：

- 设备当前状态列表；
- 单设备当前状态详情。

查询直接读取内存当前状态，不经过“实时值写 SQLite 再查询”的路径。

HTTP Handler 只做参数 / DTO / 响应转换，不能直接操纵串口或触发一次临时采集。

## 12. 前端方案

新增采集业务页面，不复用“系统管理”作为业务归属。

建议信息架构：

```text
设备采集
├─ 通信通道
├─ 设备管理
└─ 实时数据
```

### 12.1 通信通道

RS485 通道列表与新增 / 编辑表单。

### 12.2 设备管理

馈电保护器列表与新增 / 编辑表单，设备类型第一阶段只有馈电保护器。

### 12.3 实时数据

采用：

```text
设备实时状态列表
→ 点击设备
→ 当前数据详情
```

页面通过 HTTP 定时轮询获取内存当前状态。第一阶段建议默认 1～2 秒刷新，实际实现时选择一个固定默认值即可，不需要让用户配置刷新频率。

当数据已经过期或设备通信异常时，UI 必须显式展示状态 / 更新时间，不能只展示最后数值。

## 13. 开发机联调策略

第一阶段先在开发机完成，因此采集 I/O 必须具备可测试 seam，但不建设复杂模拟平台。

推荐两层验证：

1. 协议解析单元测试：固定寄存器字节 / word 输入，验证业务字段、比例、状态位；
2. 串口集成验证：使用虚拟串口 / PTY + 可控 Modbus RTU 模拟端验证轮询、超时、CRC / 异常响应、同总线多 Slave。

有真实馈电保护器可用时，再以同一运行链路接真实串口验证；不为模拟器单独开发第二套业务代码。

## 14. 测试策略

至少覆盖：

- 馈电保护器协议解析单元测试；
- 当前状态并发读写 / race test；
- 离线阈值与恢复状态测试；
- SQLite / PostgreSQL 两套配置 CRUD 与 migration 契约；
- 同一路串口多个 Slave 的顺序采集测试；
- 某一 Slave 超时后其他 Slave 继续采集；
- API 当前状态契约；
- React 页面 API mock / 关键交互测试（按现有前端测试能力）；
- `go test ./...`、`go vet ./...`、前端 lint/build。

对串口时序敏感的验证优先使用可控测试时钟或宽松边界，避免 CI 中大量 `sleep` 形成脆弱测试。

## 15. 关键技术取舍

### 15.1 不做“每设备一个无限自由 goroutine”

RS485 物理上仍要串行，过度并发最终还需要锁回串行，反而让超时、关闭和公平性更难推理。因此运行单元以物理通道为核心。

### 15.2 不把实时数据放 SQLite

页面查询当前值直接读内存。SQLite 只保存配置，避免高频写入、锁竞争和无意义历史增长。

### 15.3 不做通用寄存器配置器

当前已有完整馈电保护器协议资料。先用代码适配获得清晰、可测试的业务模型；后续真实出现大量仅寄存器表不同的设备后，再评估配置化是否值得。

### 15.4 不做 WebSocket / SSE

第一阶段数据规模约几十台设备，HTTP 1～2 秒轮询足以满足开发 / 联调页面。先降低系统复杂度。

### 15.5 不为未来 MQTT / 告警提前建立内部消息总线

当前状态更新直接进入进程内当前状态存储。未来 MQTT / Modbus Server 可以消费稳定的业务当前状态边界，但本阶段不预建事件总线。

## 16. 开发 Ticket 拆分原则

Issue #1 是总 Spec，不直接作为一个“大提交”一次实现。

后续 Ticket 按纵向能力拆分，并遵循依赖顺序：

```text
配置基础
  ↓
RS485 / Modbus RTU 基础
  ↓
馈电保护器单设备采集
  ↓
多设备与故障隔离
  ↓
当前状态 API
  ↓
React 页面闭环
  ↓
阶段集成验收
```

每个 Ticket 都必须有独立可验证结果；下一 Ticket 可以依赖上一 Ticket，但不得顺手混入 MQTT、告警、控制或 Modbus Server。
