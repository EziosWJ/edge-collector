# 第一阶段技术方案：馈电保护器 RS485 Modbus RTU 原始寄存器采集闭环

> 状态：Accepted for implementation
>
> 范围基线：Issue #1 + ADR-0011 + ADR-0013 + ADR-0014。
>
> 本文进入技术方案层：决定模块职责、运行拓扑、依赖与数据流；除非实现验证证明必要，不在此处固定大量函数签名和细粒度接口。

## 1. 目标与非目标

第一阶段只实现：

```text
馈电保护器
  ↓
RS485 + Modbus RTU
  ↓
按读取块持续采集原始寄存器
  ↓
进程内存当前状态
  ↓
HTTP 查询
  ↓
React 页面轮询展示
```

配置保存到所选 PostgreSQL 或 SQLite 数据库；实时采集结果不逐轮写入数据库。

第一阶段不实现设备协议解析、MQTT、告警、高开保护器、TCP/UDP、远程控制、Modbus Server、历史时序存储、SSE/WebSocket、通用寄存器解释器和通用插件平台。

## 2. 与现有工程的集成方式

现有项目继续保持模块化单体。

- `cmd/api` 继续作为 composition root，创建数据库、业务服务、采集运行时和 HTTP Server，并负责统一启动 / 停止。
- `internal/app` 继续负责 Gin 路由装配，不承载采集循环。
- 新增采集领域模块，不创建独立进程或微服务。
- React 管理后台继续沿用现有显式路由和 API Client 组织方式。

采集运行时是与 HTTP Server 并列的后台能力，而不是由某个 HTTP 请求触发的临时任务。

## 3. 后端模块边界

第一阶段建议建立一个明确的 `acquisition` 业务边界，避免一开始拆成大量抽象层。

建议职责：

```text
internal/acquisition
├─ 持久配置
│  ├─ RS485 通信通道
│  ├─ 设备配置
│  └─ 寄存器读取块
├─ 当前状态
│  └─ 进程内存中的设备实时状态
├─ 采集运行时
│  ├─ 加载启用配置
│  ├─ 按通信通道组织设备
│  ├─ 周期性执行采集
│  └─ 更新当前状态
├─ 原始寄存器采集
│  └─ FC03 / FC04 响应 → 按地址排列的 uint16 值
└─ HTTP
   ├─ 配置管理
   └─ 当前状态查询
```

如实现过程中代码量增大，可在 `internal/acquisition` 下按 `transport`、`protocol`、`runtime` 等职责形成子包；第一批 Ticket 不为了目录形式先创建空抽象。

## 4. 持久数据模型

第一阶段维护三类持久配置。

### 4.1 RS485 通信通道

至少表达：

- 唯一 ID；
- 名称；
- 串口设备路径 / 端口名；
- 波特率；
- 数据位；
- 停止位；
- 校验方式；
- 通信超时；
- 是否启用；
- 创建 / 更新时间等已有项目通用字段。

### 4.2 设备

至少表达：

- 唯一 ID；
- 名称；
- 设备类型；
- 所属通信通道；
- Modbus Slave 地址；
- 采集周期；
- 连续失败离线阈值，默认 3；
- 是否启用；
- 创建 / 更新时间等已有项目通用字段。

第一阶段设备类型只实现 `馈电保护器`，但数据库字段应能表达设备类型，避免未来增加高开保护器时修改设备主表的基本语义。

设备类型在本阶段只表达设备业务身份，不决定读取地址，也不触发协议解析。

### 4.3 寄存器读取块

每台设备可维护多个读取块：

- 唯一 ID；
- 所属设备；
- 同设备内唯一名称；
- 功能码，只允许 FC03 或 FC04；
- 零基起始地址；
- 寄存器数量，范围 `1～125`；
- 排序号。

起始地址与数量形成的范围不得超过 `0～65535`。同一设备、同一功能码下的读取块不得重叠；FC03 与 FC04 属于不同寄存器区，允许使用相同数字地址。读取块不设置启用状态，也不保存数据类型、字节序、word order、倍率、单位或状态位语义。

### 4.4 Migration

继续遵循项目现有 PostgreSQL / SQLite 双 migration 树、逻辑版本锁步规则。

寄存器读取块使用下一逻辑版本的 PostgreSQL / SQLite Goose migration 同步增加。不得使用 GORM `AutoMigrate()` 替代 migration。

## 5. Modbus 与串口依赖

第一阶段采用：

- `github.com/simonvetter/modbus` 作为 Modbus Client 基础实现；
- 第一阶段只启用其 RS485 / Modbus RTU 能力；
- 第三方 Modbus 库必须隔离在采集基础设施边界，当前状态和 HTTP DTO 不得直接依赖该库类型；
- 在采集基础设施边界内封装串口会话、Slave 切换和 Modbus 请求。

选择理由：

1. 原生支持串口 Modbus RTU，并同时支持 Modbus TCP、RTU over TCP、Modbus TCP over UDP 和 RTU over UDP，与 Edge Collector 后续已确认的 TCP / UDP / RTU over UDP 路线匹配；
2. 提供直接返回 16-bit 寄存器数组的 FC03 / FC04 读取能力，满足本阶段原始寄存器采集；
3. 同时提供 Client 和 Modbus TCP Server 能力，虽然第一阶段不使用 Server，但与完整产品后续 Modbus Server 方向更一致；
4. 项目仍在维护，RTU 传输层已有针对串口 RX 缓冲旧数据等现场问题的修复；
5. 直接复用成熟 CRC、RTU 帧和串口实现，避免自行实现 Modbus RTU 协议栈。

### 5.1 隔离与可替换约束

选用 `simonvetter/modbus` 不意味着业务层绑定该库。

必须保持以下依赖方向：

```text
寄存器读取块 / 采集运行时 / 当前状态
                ↓
      项目自身的采集 I/O 边界
                ↓
     simonvetter/modbus + serial
```

禁止让当前状态结构和 HTTP DTO 直接包含 `simonvetter/modbus` 的 Client 或错误类型。跨越 I/O 边界的数据使用项目自己的读取请求和 `[]uint16` 表示。

如果开发机 PTY 或后续 RK3568 实机验证发现其串口断线恢复、取消语义或现场稳定性不能满足要求，应允许仅替换基础设施实现，而不重写读取块、采集调度和页面 API。

第一阶段必须通过 PTY / 虚拟串口覆盖至少以下失败场景：超时、无响应、异常响应、重新恢复通信。是否需要在库外增加 reopen / retry 策略，根据这些测试结果决定，不在技术方案阶段提前写死。

## 6. 运行拓扑：按物理通信通道串行执行

RS485 是共享总线，同一物理串口上的 Modbus 事务必须串行。

第一阶段采用以下运行拓扑：

```text
Acquisition Runtime

RS485 Channel A
  └─ 单一串行采集循环
      ├─ Device 1
      ├─ Device 2
      └─ Device N

RS485 Channel B
  └─ 单一串行采集循环
      ├─ Device 1
      └─ Device N
```

核心原则：

- 同一路 RS485 任何时刻只执行一个 Modbus 事务序列；
- 不同物理串口独立运行，Channel A 的超时不能阻塞 Channel B；
- 同通道设备按各自采集周期获得执行机会；
- 单台设备超时结束后继续处理后续设备；
- 不为每个寄存器读取建立无界 goroutine；
- 第一阶段不引入全局 worker pool、消息队列或复杂优先级调度器。

具体使用 ticker、timer、最小堆或简单 next-due 调度可在实现 Ticket 中根据测试选择，但必须满足以上可观测语义。

## 7. 生命周期

采集运行时随 API 进程启动：

```text
加载应用配置
→ 打开数据库
→ 构建 acquisition 配置服务 / 当前状态存储
→ 从 SQLite 读取启用的 RS485 通道和设备
→ 启动 Acquisition Runtime
→ 启动 HTTP Server
```

停止时：

```text
收到 SIGINT / SIGTERM
→ 停止接受新的采集周期
→ 取消正在等待的采集上下文
→ 关闭串口资源
→ 停止 HTTP Server
→ 关闭数据库
```

采集运行时必须纳入现有 graceful shutdown，不允许后台 goroutine 在进程退出路径上失控。

通信通道、设备和读取块配置在数据库事务提交成功后通知运行时刷新。当前设备采集完成后再应用新快照，不中断正在执行的 Modbus 请求；具体边界沿用 ADR-0013。

## 8. 寄存器读取与原始值边界

第一阶段不假定厂家寄存器表已经确认，也不产出业务实时数据。

每台启用设备按照读取块排序依次执行：

```text
读取块（FC03 / FC04、起始地址、数量）
→ Modbus 请求
→ 传输校验后的 []uint16
→ 逐个关联零基地址
→ 更新读取块当前快照
```

一个读取块成功时，该块所有寄存器作为同一批次更新。单个读取块失败后继续处理后续读取块，使同一设备的其他块仍有机会更新。

当前边界只保留每个寄存器的 16-bit 无符号数值。HEX、DEC、BIN 是前端对同一数值的文本表示，不是三份数据，也不改变 API 契约。

完整 RTU 响应帧、CRC 和原始字节流不进入当前状态。厂家协议确认后，有符号数、浮点数、多寄存器组合、倍率、单位和状态位解析应作为消费原始寄存器快照的后续能力单独设计。

## 9. 当前状态模型

当前状态只存在于进程内存。

每台设备至少维护：

```text
Device Current State
├─ Device ID
├─ Register Blocks
│  ├─ 读取块配置标识
│  ├─ 按零基地址排列的 uint16 当前值
│  ├─ 本轮有效性
│  ├─ 最近尝试时间
│  ├─ 最后成功时间
│  └─ 最近错误
├─ 最近一次采集尝试时间
├─ 最近一次成功时间
├─ 通信状态
├─ 连续失败次数
└─ 最近错误信息
```

读取块首次成功前也创建地址行，值为空。失败读取块保留上次成功值，但整块标记为本轮无效；读取范围变化时清除旧快照，只有名称或排序变化时保留快照。

第一阶段当前状态存储的要求：

- 进程内并发安全；
- 读接口不能阻塞串口通信；
- 更新以读取块为边界保持一致快照；
- 容量由已配置设备数决定，不允许随采集周期无限增长；
- 不保存历史序列。

本方案不强制 store 的具体 map / mutex / atomic.Value 结构，由实现根据 race test 与可读性决定。

## 10. 通信状态状态机

第一阶段不需要复杂设备健康模型，但应统一以下状态变化：

```text
启动 / 尚未成功采集
        ↓
所有读取块成功 ───────→ ONLINE
        ↑                  │
        │                  │ 部分读取块失败
        │                  ↓
        └──────────── DEGRADED / FAILED
                           │
                           │ 所有读取块连续失败达到阈值（默认 3）
                           ↓
                        OFFLINE
```

部分成功时保持 `DEGRADED`，并中断“所有读取块连续失败”的计数；只有下一轮所有读取块成功才恢复 `ONLINE`。

实际枚举名称可在实现中调整，但 API 和页面必须能区分：尚无数据、在线、近期失败、离线。

## 11. HTTP API 方案

第一阶段新增两类 HTTP 能力。

### 11.1 配置管理

提供 RS485 通道、设备和设备内寄存器读取块的配置能力，以项目现有认证 / 响应 / 审计模式接入。读取块在设备新增 / 编辑表单中维护，不建立独立管理页面。

建议新业务 API 使用 `/api/v1/...`，不继续把采集领域塞进 `/api/system`。

具体路由名称由实现确定，但建议资源语义保持：

```text
/api/v1/acquisition/channels
/api/v1/acquisition/devices
```

### 11.2 当前状态查询

提供：

- 设备当前状态列表；
- 单设备当前状态详情。

查询直接读取内存当前状态，不经过“实时值写 SQLite 再查询”的路径。

现有 `/api/v1/acquisition/states` 路径保持不变，设备数据改为 `registerBlocks`。API 返回数值型 16-bit 无符号寄存器值，不返回预格式化的 HEX / DEC / BIN 字符串。

HTTP Handler 只做参数 / DTO / 响应转换，不能直接操纵串口或触发一次临时采集。

## 12. 前端方案

新增采集业务页面，不复用“系统管理”作为业务归属。

建议信息架构：

```text
设备采集
├─ 通信通道
├─ 设备管理
└─ 实时寄存器
```

### 12.1 通信通道

RS485 通道列表与新增 / 编辑表单。

### 12.2 设备管理

馈电保护器列表与新增 / 编辑表单，设备类型第一阶段只有馈电保护器。设备表单通过可增删、可排序的行维护多个读取块。

### 12.3 实时寄存器

采用：

```text
设备实时状态列表
→ 点击设备
→ 按读取块分组的寄存器表
```

页面通过 HTTP 定时轮询获取内存当前状态。第一阶段建议默认 1～2 秒刷新，实际实现时选择一个固定默认值即可，不需要让用户配置刷新频率。

每行展示读取块名称、功能码、零基十进制地址、当前值、本轮有效性和最后成功时间；读取块级展示最近尝试时间与错误。当前值默认使用四位 HEX，页面级全局切换为无符号 DEC 或 16 位 BIN，地址始终保持十进制。

当数据尚未取得、已经过期或设备通信异常时，UI 必须显式展示空值、有效性、状态和更新时间，不能只展示最后数值。

## 13. 开发机联调策略

第一阶段先在开发机完成，因此采集 I/O 必须具备可测试 seam，但不建设复杂模拟平台。

推荐两层验证：

1. 原始寄存器单元测试：固定 FC03 / FC04 响应，验证地址和值保持 16-bit 无符号语义；
2. 串口集成验证：使用虚拟串口 / PTY + 可控 Modbus RTU 模拟端验证多个读取块、轮询、超时、异常响应和同总线多 Slave。

有真实馈电保护器可用时，再以同一运行链路接真实串口验证；不为模拟器单独开发第二套业务代码。

## 14. 测试策略

至少覆盖：

- 读取块校验、排序、FC03 / FC04 和原始寄存器快照单元测试；
- 当前状态并发读写 / race test；
- 全成功、部分成功、全部连续失败与恢复状态测试；
- SQLite / PostgreSQL 两套配置 CRUD 与 migration 契约；
- 读取块热刷新及读取范围变化后清除旧快照测试；
- 同一路串口多个 Slave 的顺序采集测试；
- 某一 Slave 超时后其他 Slave 继续采集；
- API 当前状态契约；
- React 页面 API mock / 关键交互测试（按现有前端测试能力）；
- `go test ./...`、`go vet ./...`、前端 lint/build。

对串口时序敏感的验证优先使用可控测试时钟或宽松边界，避免 CI 中大量 `sleep` 形成脆弱测试。

## 15. 关键技术取舍

### 15.1 不做“每设备一个无限自由 goroutine”

RS485 物理上仍要串行，过度并发最终还需要锁回串行，反而让超时、关闭和公平性更难推理。因此运行单元以物理通道为核心。

### 15.2 不把实时数据放 SQLite

页面查询当前值直接读内存。数据库只保存配置，避免高频写入、锁竞争和无意义历史增长。

### 15.3 只配置读取范围，不配置协议解释

第一阶段允许配置 FC03 / FC04 读取块，以便在厂家协议尚未确认时观察真实寄存器。读取块不包含数据类型、字节序、倍率、单位或状态位；这些协议解释规则在确认厂家资料后单独设计。

### 15.4 不做 WebSocket / SSE

第一阶段数据规模约几十台设备，HTTP 1～2 秒轮询足以满足开发 / 联调页面。先降低系统复杂度。

### 15.5 不为未来 MQTT / 告警提前建立内部消息总线

当前原始寄存器快照直接进入进程内当前状态存储。未来先形成经过确认的业务实时数据，再由 MQTT / Modbus Server 消费；本阶段不预建事件总线。

## 16. 开发 Ticket 拆分原则

Issue #1 是总 Spec，不直接作为一个“大提交”一次实现。

后续 Ticket 按纵向能力拆分，并遵循依赖顺序：

```text
配置基础与寄存器读取块
  ↓
RS485 / Modbus RTU 基础
  ↓
单设备原始寄存器采集
  ↓
多设备与故障隔离
  ↓
当前状态 API
  ↓
React 页面闭环
  ↓
阶段集成验收
```

每个 Ticket 都必须有独立可验证结果；下一 Ticket 可以依赖上一 Ticket，但不得顺手混入 MQTT、告警、控制或 Modbus Server。
